Intune 신뢰 인증서 배포

INTUNE CERTIFICATE TRUST DEPLOYMENT

Build the trust chain before certificate-based access

Trusted root and intermediate certificates must be delivered and validated before Wi-Fi, VPN, SCEP, PKCS or app authentication scenarios depend on them.

CARoot
CERDER
IntuneDeploy
TrustVerify

Executive Summary​

Trusted Root CA certificates must be deployed before PKCS, SCEP, or imported certificate profiles can be used successfully.

This guide explains the deployment process using Intune Trusted Certificate Profiles.

A trusted certificate profile supports root and intermediate CA certificates only. SCEP and PKCS profiles request a certificate for the user or device. An imported PKCS profile distributes an existing certificate. The trusted certificate profile distributes the CA public certificate used to establish trust. Create a separate trusted certificate profile for each platform and assign it to the same groups as the certificate profiles that depend on it. See Microsoft's trusted certificate profile requirements.

한국어 요약​

Intune의 신뢰 인증서 프로필은 Wi-Fi, VPN과 업무 앱에서 인증서를 신뢰하도록 루트·중간 인증서를 배포하는 데 사용합니다.

먼저 발급 기관의 공개 인증서를 DER 형식의 .cer 파일로 내보내세요. 개인 키가 든 .pfx 파일은 이 프로필에 올리지 않습니다.

  • SCEP — SCEP 프로필에서 신뢰 인증서 프로필을 직접 선택합니다.
  • PKCS — PKCS 프로필에는 발급 기관 서버를 지정합니다. 신뢰 인증서 프로필은 같은 대상 그룹에 따로 할당합니다.
  • 가져온 PKCS 인증서 — 이미 발급된 인증서를 배포합니다. 기기가 발급 기관을 신뢰하는지 확인하고 신뢰 인증서 프로필도 같은 그룹에 할당합니다.

Microsoft의 프로필별 신뢰 관계 설명

Prerequisites​

Required certificates:

  • Root CA Certificate
  • Intermediate CA Certificate, when present in the issuing chain

Export requirements:

  • DER encoded .CER file
  • Public certificate only
  • No private key (.PFX)

Architecture​

Certificate trust chainCA to managed device
01Certificate AuthorityConfirm root and intermediate CA certificates that must be trusted by devices.
02Export certificateUse DER encoded .CER format and public certificate only.
03Deploy with IntuneCreate Trusted Certificate profile and assign to validated target groups.
04Validate device trustConfirm root and intermediate stores before SCEP, PKCS, Wi-Fi or VPN rollout.

Deployment Process​

Deployment workflowProfile, assignment, validation
01Create profileIn the Intune admin center, go to Devices > Manage devices > Configuration > Create. Select the platform, then Trusted certificate or Templates > Trusted certificate, as available.
02Upload and assignUpload the certificate and target user, device or dynamic groups.
03Deploy and monitorSync devices, review policy status and troubleshoot profile delivery.
04EvidenceRecord validation result before enabling certificate-dependent services.

Recommended execution notes:

  • Start with a pilot group before broad assignment.
  • Deploy the root and intermediate chain in the correct order.
  • Keep certificate owner, renewal date and dependent service documented.
  • Validate both device certificate store and application behavior.

Validation​

Match validation to the Destination Store selected in the Intune profile. For Windows, the trusted certificate profile supports Computer Root, Computer Intermediate and User Intermediate stores. Official profile guidance describes the choices.

DestinationCorrect validation view
Computer Rootcertlm.msc → Trusted Root Certification Authorities, or Cert:\LocalMachine\Root
Computer Intermediatecertlm.msc → Intermediate Certification Authorities, or Cert:\LocalMachine\CA
User Intermediatecertmgr.msc in the affected user's context, or Cert:\CurrentUser\CA

Read-only PowerShell checks:

Get-ChildItem Cert:\LocalMachine\Root | Select-Object Subject, Thumbprint, NotAfter
Get-ChildItem Cert:\LocalMachine\CA | Select-Object Subject, Thumbprint, NotAfter
# Run as the target user when the profile uses User Intermediate.
Get-ChildItem Cert:\CurrentUser\CA | Select-Object Subject, Thumbprint, NotAfter

Compare the expected thumbprint, chain and expiration, then test the dependent Wi-Fi/VPN/application scenario. Merely finding a certificate in the current user's store does not prove a Computer Root deployment succeeded.

Deployment Decision Points​

Certificate deployment should be treated as an identity and device trust dependency. Before assigning a Trusted Certificate profile broadly, confirm which downstream scenario needs the certificate: Wi-Fi, VPN, SCEP, PKCS, email signing, browser trust or line-of-business application access. The assignment scope should match that scenario rather than every managed device by default.

Key decisions:

  • whether the certificate is required for user devices, shared devices or servers
  • whether the profile should target users, devices or dynamic groups
  • whether the CA chain requires both root and intermediate certificates
  • how renewal, revocation and CA rollover will be handled
  • who owns validation when certificate-dependent services fail
