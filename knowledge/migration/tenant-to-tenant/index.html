Microsoft 365 테넌트 간 마이그레이션

Executive Summary​

A tenant-to-tenant migration program coordinates account preparation, supported content moves and the recreation or reconfiguration of target governance controls. The migration tool does not automatically transfer every identity, policy or workload.

Typical business drivers include:

  • Merger & Acquisition
  • Divestiture
  • Global IT Consolidation
  • Regulatory Separation
  • Tenant Rationalization

Unlike simple mailbox migrations, Tenant-to-Tenant projects impact identity, collaboration, security, compliance and end-user productivity.

The objective is to minimize business disruption while preserving data integrity, permissions and governance.

Migration Methods​

Microsoft Migration Orchestrator coordinates Exchange mailboxes, OneDrive, Teams chats and Teams meetings. It moves content, not identities; prepare identity mapping and the required user configuration separately. Teams meetings require both chats and mailbox migration in the batch. SharePoint sites, Teams channels, apps and device policies need separate migration plans. Check the per-user Cross Tenant User Data Migration add-on and workload exclusions in the orchestrator documentation.

Identity Mapping requires a mailbox in the source tenant and a MailUser without a mailbox in the target tenant, even when the batch does not move mailboxes. For OneDrive, the native orchestrator moves content and leaves a redirect; it does not support incremental or delta migration passes. CompleteAfterDate starts the remaining workloads after Exchange cutover rather than guaranteeing that every workload is complete at that time. Plan the user outage around these dependencies; migration completion is not covered by an SLA.

Limitations​

For the native orchestrator's Teams chats and meetings, source content remains, potentially with changed participant lists or duplicate threads in either tenant. After migration, users should work with their target identity. Access to out-of-scope source content still requires a licensed source user, so do not remove source access merely because mailbox migration has finished. See Teams chat and meeting scope.

Data Protection​

Review:

  • Sensitivity Labels
  • DLP
  • Retention

Native cross-tenant mailbox moves are blocked for mailboxes on hold. After a successful move, the source mailbox is deleted and is not available for investigation in the source tenant. This is a move, not a reversible copy; an ordinary source-side rollback plan is insufficient. Review holds, preservation obligations, user-visible content scope and post-move routing before the migration. See the current mailbox move conditions.

Success Criteria​

Define acceptance per workload and reconcile every skipped or failed item. The percentages below are illustrative planning targets, not a Microsoft service guarantee or permission to lose one percent of the data. Unexplained missing critical content is a cutover blocker; record approved exclusions separately.

  • Data Integrity > 99%
  • Migration Success Rate > 99%

Business​

  • User Satisfaction

Best Practice​

  • Assess before migrating
  • Validate identity first
  • Pilot before production
  • Communicate frequently
  • Migrate governance, not just data
  • Validate permissions carefully
  • Plan coexistence early

Lessons Learned​

  • Inventory identity dependencies and target-account requirements
  • Test SharePoint permissions with representative users
  • Validate tooling and communicate the expected user impact
  • Teams migrations require extensive validation
  • Security baselines should be rebuilt before cutover
  • Assign support owners and response times for executives and other high-impact users
