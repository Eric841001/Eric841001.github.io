Exchange Online 아키텍처와 마이그레이션

Executive Summary​

Exchange Online is Microsoft's enterprise cloud messaging platform and serves as the foundation for modern communication and collaboration.

A successful Exchange Online deployment requires more than mailbox migration.

Organizations must evaluate:

  • Identity architecture
  • Mail routing design
  • SMTP relay requirements
  • Security controls
  • Compliance requirements
  • Hybrid coexistence
  • Global subsidiary requirements

The objective is to establish a secure, resilient and globally scalable messaging platform.

Business Scenario​

Common customer scenarios:

Scenario 1​

Exchange Server to Exchange Online

Examples:

  • Exchange Server Subscription Edition (SE)
  • Legacy Exchange 2013, 2016 or 2019 estates requiring a supported transition plan

Exchange 2013 reached end of support on April 11, 2023; Exchange 2016 and 2019 reached end of support on October 14, 2025. Treat them as legacy migration sources, not a current supported deployment baseline. See the Exchange lifecycle guidance.

Goal:

Modernize messaging platform and reduce infrastructure dependency.

Scenario 2​

Google Workspace to Microsoft 365

Goal:

Unify collaboration and messaging platform.

Scenario 3​

Tenant-to-Tenant Migration

Examples:

  • M&A
  • Divestiture
  • Group consolidation

Goal:

Consolidate users, domains and messaging systems.

Scenario 4​

Global Mail Consolidation

Examples:

  • Headquarters and subsidiaries
  • Multi-domain environment

Goal:

Centralized governance with localized operations.

Migration Approaches​

Cutover Migration​

Cutover moves the organization in one event. Microsoft documents a maximum of 2,000 mailboxes and recommends 150 or fewer for a manageable migration window. The 150 figure is a planning recommendation, not a technical hard limit. Confirm source-version prerequisites and directory synchronization constraints in the cutover procedure.

Staged Migration​

Staged migration was the legacy method for Exchange 2003 or 2007. Staged OutlookAnywhere onboarding retired on May 8, 2025; do not select it for a new migration. Evaluate a supported migration path for the source environment, such as hybrid remote onboarding where its prerequisites are met. See the retirement notice.

Hybrid Migration​

Use hybrid remote moves when the supported source configuration and coexistence requirements justify them. Validate the Hybrid Configuration Wizard prerequisites, identity synchronization, certificates, mail routing and free/busy before selecting the approach. Organization size alone does not determine the migration method. See Exchange hybrid deployments.

Tenant-to-Tenant Migration​

Suitable:

  • Merger
  • Acquisition
  • Divestiture

Tools:

  • Microsoft Migration Orchestrator for supported workloads
  • Quest
  • BitTitan
  • AvePoint Fly

Microsoft Migration Orchestrator coordinates Exchange mailboxes, OneDrive, Teams chats and Teams meetings. It moves content, not identities; prepare identity mapping and the required user configuration separately. Teams meetings require both chats and mailbox migration in the batch. SharePoint sites, Teams channels, apps and device policies need separate migration plans. Check the per-user Cross Tenant User Data Migration add-on and workload exclusions in the orchestrator documentation.

Best Practice​

  • Use pilot migrations before production rollout
  • Validate mail flow before cutover
  • Disable legacy authentication
  • Implement MFA before migration
  • Review external forwarding policies
  • Establish rollback procedures
  • Communicate frequently with business users

Lessons Learned​

  • Mail migration is primarily a business project, not a technical project
  • Plan user communication alongside the migration tooling and cutover tasks
  • Test coexistence mail flow, calendar access and client behavior with pilot users
  • Document DNS changes, propagation checks and the rollback decision before cutover
  • Security controls should be implemented before migration
  • Global deployments require regional coordination

캐나다 시간대 변경 후 일정 점검​

2026년 11월 1일 캐나다의 대상 지역은 시계를 한 시간 뒤로 돌리지 않았습니다. British Columbia는 UTC−07:00, Alberta는 UTC−06:00, Manitoba는 UTC−05:00을 유지하며, 일부 인접 지역도 영향을 받습니다.

해당 지역의 사용자는 Windows를 업데이트하고 Outlook에서 새 시간대를 선택해야 합니다. 기존 일정은 자동으로 이전되지 않으므로 11월 1일 이후의 단일·반복 회의와 참석자의 표시 시간을 확인하세요. 한국 사용자도 해당 지역과의 회의가 있다면 초대장 시간을 함께 대조하세요.

11월 2일 개정된 공식 안내에서는 제품별 상태 표와 권장 작업 모두 단일 회의 보정용 Exchange Online PowerShell 명령의 목표일을 11월 4일로 안내합니다. 11월 5일 확인 시점에도 제공 완료 공지는 없고, 반복 회의 보정 일정은 미정입니다. 목표일이 지났다는 이유만으로 배포가 끝났다고 판단하지 말고 현재 공식 안내에서 제공 상태와 적용 절차를 확인하세요.
