한글 요약조건부 액세스 정책을 켜기 전에 누구의 어떤 로그인이 영향을 받는지 확인하세요. 긴급 접근 계정의 로그인 경로와 위험 사용자의 복구 절차도 함께 점검할 수 있습니다.

Identity and Access Control

Design Conditional Access as the policy engine for Zero Trust and Copilot-ready Microsoft 365

Conditional Access decides who can access what, from where, on which device and under which risk. A good design protects users and data without locking out business-critical work.

Security LandingZero TrustRequest CA Matrix
Design ModelReport-only first
01LayerSeparate baseline MFA, admin protection, device, app and risk policies.02DeployUse report-only, pilot scope, exclusions, sign-in logs and staged enforcement.03ProtectKeep emergency access, exception ownership and expiry under governance.04CopilotAlign Copilot access with identity, device, session and data protection policy.
Policy is the new perimeterConditional Access evaluates applicable policies after first-factor authentication. Continuous Access Evaluation supports near-real-time enforcement only for supported resources and events.

memberOf 그룹을 정책 대상으로 사용하는 경우​

종료된 기존 memberOf 미리 보기 방식의 그룹은 2026년 11월 3일 이후 구성원이 갱신되지 않습니다. 후속 MemberOf Next로 전환하려면 Entra ID Governance와 Standard 우선순위가 필요합니다. 전환 후에도 하루 두 번 갱신되므로, 즉시 접근을 차단해야 하는 용도로 의존하지 마세요. ID 설계 문서의 전환 안내에 따라 처리 상태와 정책의 포함·제외 대상, 실제 로그인 결과를 확인합니다. 긴급 접근 계정의 제외 설정도 함께 확인하세요.

License and rollout verification — 2026-10-25​

Microsoft's overview requires Entra ID P1 for Conditional Access; Business Premium also includes access. User/sign-in risk policies require P2, as described in Entra licensing.

Agent policies have separate licensing and identity targeting rules. The current agent policy documentation lists Microsoft 365 E7, or Microsoft Agent 365 paired with at least Entra P1 or Microsoft 365 E3, as licensing options. The general overview still marks agent targeting as preview; verify the specific policy's release status in the linked scenario documentation and your tenant rather than declaring all agent controls GA or preview together. A policy targeting an agent identity does not automatically cover delegated user access or an agent user account. Validate the token subject, policy target and report-only results before enforcement.

Microsoft 관리형 정책과 위험 해결​

Microsoft가 만든 정책도 직접 만든 정책과 함께 점검해야 합니다. 관리 센터의 Entra ID > Conditional Access > Policies에서 Created by가 Microsoft인 항목을 찾고 대상·예외·현재 상태를 확인하세요.

  • 자동 활성화: 처음에는 보고 전용으로 생성되며, 보통 도입 후 최소 30일이 지나면 활성화됩니다. 일부 정책은 더 빨리 적용될 수 있으므로 메시지 센터와 정책 상세의 테넌트별 일정을 확인하세요. 보고 전용 상태로 두는 것만으로 적용이 계속 미뤄지지는 않습니다.
  • 고위험 사용자: Require remediation for high-risk users는 Entra ID P2 대상 정책입니다. Conditional Access: User Risk remediation 그룹으로 범위를 정합니다. Microsoft는 사용 가능한 P2 라이선스 수를 한도로 MFA에 등록한 적격 활성 사용자를 이 그룹에 추가하며, 로그인 위험이 아닌 사용자 위험을 해결합니다. 외부·게스트 사용자는 지원하지 않습니다.
  • 인증과 정책 충돌: 인증 강도와 매번 로그인 조건이 자동 적용됩니다. Block은 위험 해결보다 우선하고, 위험 해결은 암호 변경 요구보다 우선합니다. 기존 정책과 중복 적용되는지 확인하세요.
  • 잠금 방지: 긴급 접근 계정을 제외하고 MFA 등록 상태를 점검하세요. 하이브리드 환경에서는 암호 해시 동기화 등 암호 변경 전제 조건도 확인해야 합니다. MFA 후 수행하는 보안 암호 변경과 암호를 모를 때 쓰는 SSPR 복구 절차를 구분하세요.

고객이 만든 사용자 위험 정책이 켜져 있으면 이 관리형 정책은 생성되지 않습니다. 기존 사용자 위험 정책이 Report-only나 Off이면 생성될 수 있습니다. 다른 종류의 조건부 액세스 정책이 있다는 이유만으로 생성 대상에서 제외되지는 않습니다.

보고 전용 결과와 로그인 기록을 검토한 뒤 적용 범위를 정하세요. 활성화 일정은 테넌트마다 다를 수 있습니다.

Executive Summary​

Microsoft Entra Conditional Access is the policy enforcement engine of Microsoft's Zero Trust architecture. It evaluates user identity, device posture, location, application, risk signals and session context before granting access to corporate resources.

This document provides an enterprise design methodology for Microsoft 365, Azure, Security and Copilot deployments.

한국어 요약​

Conditional Access는 사용자, 접속 기기·위치·앱과 위험 신호를 확인해 접근 조건을 적용하는 Entra ID 기능입니다.

먼저 보고 전용 모드에서 로그인 기록을 살펴보세요. 사용자 작업(User actions)을 대상으로 하는 정책은 이 모드로 평가할 수 없습니다. 기기 준수 여부를 검사하면 macOS·iOS·Android에서는 인증서 선택 창이 뜰 수 있습니다. Microsoft의 보고 전용 모드 안내 로그인 기록으로 정책 적용 결과를 확인한 뒤 범위를 넓히세요.

Copilot은 사용자의 Microsoft 365 자료 접근 권한을 따릅니다. 계정과 기기, 세션과 데이터 보호 정책을 함께 검토하세요.

Zero Trust Evaluation Flow​

Mobile policy control change — 2026-10-25​

The Require approved client app grant control moved to a read-only state on 2026-06-30. Existing enabled policies can continue to enforce, but administrators cannot create or edit policies using that control. For new policies, use Require app protection policy and verify application support, enrollment model and user impact in report-only mode. See Microsoft's migration guidance.

Blocking legacy authentication and disabling a mail protocol are separate decisions. A protocol that uses OAuth is not Basic authentication merely because it is POP, IMAP or SMTP AUTH. Document the protocol requirement and authentication flow before choosing the policy scope.

Policy Layer Model​

Layer 1Baseline MFARequire MFA for routine users. Before enforcement, check emergency access exclusions and review sign-in results.
Layer 2Admin protectionApply stricter controls to privileged roles, admin portals and management workloads.
Layer 3Legacy authentication blockBlock legacy authentication using the relevant client-app conditions. POP, IMAP and SMTP AUTH can also use OAuth; protocol names alone do not identify Basic authentication.
Layer 4Device and app controlRequire compliant devices or app protection for sensitive workloads. For new mobile policies, use Require app protection policy rather than the retired approved-client-app control.
Layer 5Risk and session controlUse user and sign-in risk conditions, Intune compliance informed by Defender device risk, and supported session controls.
Layer 6Workload-specific policiesApply tailored controls for Exchange, SharePoint, Teams, OneDrive, Azure and Copilot scenarios.

기기 위험 점수는 사용자 위험·로그인 위험과 적용 경로가 다릅니다. Defender for Endpoint와 Intune을 연결하고, Intune 준수 정책에 기기 위험 수준의 허용 기준을 설정한 뒤 조건부 액세스에서 준수 상태의 기기 요구를 적용합니다. 기기를 Defender에 등록하는 것만으로 이 접근 정책이 생기지는 않습니다. 기기 위험을 이용한 준수·조건부 액세스 구성을 참고하세요.

  • 90일 점검 — 점검 간격이 90일을 넘지 않도록 하세요. 담당자가 각 계정으로 로그인해 관리 작업을 수행하고, 보안 담당자는 사용 알림이 도착했는지 확인합니다. IT 담당자나 Entra 구독이 바뀌었을 때도 점검하세요.

Copilot Access Control​

Copilot access control should not be designed as a standalone AI policy. It should inherit the Microsoft 365 access baseline while adding AI-specific readiness checks.

IdentityPilot group and role scopeStart with selected Copilot users, privileged roles and business scenarios.
DeviceCompliant or managed deviceReview whether Copilot access should require managed devices for sensitive roles.
SessionSession and download restrictionsAlign SharePoint, OneDrive and Teams access restrictions with Copilot data exposure risk.
DataPermission hygieneConditional Access does not fix oversharing. Review data permissions and information architecture.
RiskRisk-based controlsUse user risk, sign-in risk and device risk signals for sensitive access paths.
AdoptionUser guidanceExplain why access controls exist so adoption does not become a support problem.

Common Mistakes​

ScopeApplying broad policies too quicklyUse report-only and pilot scope before organization-wide enforcement.
ExclusionsPermanent broad exclusionsEvery exclusion should have owner, reason, expiry and compensating control.
AdminNot separating admin policiesPrivileged roles need stronger controls and different monitoring than standard users.
DeviceRequiring compliance before readinessConfirm Intune enrollment, device inventory and support path before enforcing device controls.
CommunicationNo user communicationRestrictive policies without explanation create support load and user resistance.
CopilotTreating Copilot as only a license issueCopilot readiness also needs identity, device, data and session control alignment.
