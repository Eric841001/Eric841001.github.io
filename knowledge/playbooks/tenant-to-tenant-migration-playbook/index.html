Executive Summary

Tenant-to-tenant migration is not a simple data transfer project.

It requires coordinated planning across identity, domain, mail flow, Teams, SharePoint, OneDrive, security, compliance, user communication and business cutover.

This playbook provides a structured delivery model for Microsoft 365 tenant migration programs.

Executive lens: Tenant migration succeeds when identity, mail, collaboration, security and user communication are treated as one business cutover program rather than separate technical workstreams.

Microsoft 365 Tenant Migration Control Tower

Run tenant migration as a business cutover program

Tenant-to-tenant migration is not a simple data transfer. It requires coordinated planning across identity, domains, Exchange Online, Teams, SharePoint, OneDrive, security, compliance, communication and hypercare.

IdentityMailDataCutover
Tenant MigrationGlobal ConsolidationRequest Migration Assets
Control TowerCutover without surprises

Migration ruleIdentity, mail, collaboration, security and user communication must be operated as one cutover rhythm, not separate technical tracks.

Typical tenant-to-tenant migration scope includes:

  • User accounts
  • Mailboxes
  • Shared mailboxes
  • Distribution groups
  • Microsoft Teams
  • SharePoint sites
  • OneDrive data
  • Domains and aliases
  • Security policies
  • Compliance policies
  • User communication and support

Domain Cutover Sequence​

Domain cutover sequenceLower risk before DNS changes
01Prepare source tenantRemove domain dependencies, aliases, mail flow blockers and workload references.
02Prepare DNSLower TTL and confirm MX, SPF, DKIM, DMARC, Autodiscover and relay dependencies.
03Verify target tenantAdd and verify the domain in the target tenant, then activate target mail routing.
04User validationConfirm sign-in, Outlook, mobile access, internal and external mail flow after cutover.

Exchange Online Migration

For native cross-tenant mailbox moves, any hold blocks the move. A successful move deletes the source mailbox; it is no longer discoverable there. Prepare preservation requirements and a method-specific recovery plan before cutover. Do not assume the migration leaves a reversible source copy.

Cutover Activities​

This is a planning sequence, not a universal migration procedure. Native cross-tenant SharePoint moves are a one-time move and do not support incremental or delta passes. Define the freeze and final-transfer procedure separately for each workload and tool. For this native SharePoint move, keep the source site in Read/Write mode; setting it to Read-only causes migration failure. Plan how to stop user edits without changing the source to Read-only.

StepActivity
1Stop source changes
2Complete the final supported transfer and reconcile content; use a delta pass only when the selected method supports it
3Domain removal from source
4Domain verification in target
5DNS update
6Mail flow validation
7User access validation
8Executive confirmation

Advanced Tenant Consolidation Considerations

Mail Coexistence with Legacy Mail Systems​

Tenant consolidation may require mail coexistence when the headquarters and regional entities use different mail platforms.

Typical scenarios include:

  • Legacy mail platform and Exchange Online coexistence
  • Multiple Microsoft 365 tenants
  • Shared SMTP domain
  • Regional mail domain transition
  • Staged mailbox migration

Recommended Design​

AreaRecommendation
Primary SMTPPreserve user-facing address where possible
Alternate SMTPUse routing address for coexistence
Mail ContactsRepresent users from the other system
ForwardingConfigure temporary forwarding where required
Mail FlowValidate both inbound and outbound routing
CutoverPrepare rollback and validation checklist

Shared Domain and Subdomain Routing​

A custom domain can be verified in only one Microsoft 365 tenant at a time. Mail coexistence with a legacy system is different from verifying the same domain in two Microsoft 365 tenants. Design alternate routing addresses, source dependency removal, domain release and target verification before cutover.

Recommended options:

OptionUse Case
Subdomain routingLong-term coexistence or phased transition
Alternate address routingUser-level coexistence
Mail contact routingRepresent non-migrated users
Full domain cutoverFinal consolidation into target tenant

Domain Transfer Impact​

Moving a domain from one tenant to another can affect:

  • User sign-in
  • Mail reception
  • Teams identity
  • Guest access
  • External collaboration
  • Mobile mail profile
  • Outlook profile

Required Controls​

  • Lower DNS TTL before cutover
  • Freeze proxy address changes
  • Validate all aliases
  • Prepare domain removal checklist
  • Prepare target tenant verification
  • Validate MX, SPF, DKIM and DMARC
  • Communicate user sign-in impact
  • Prepare rollback plan

Purview and Sensitivity Label Migration​

If documents are protected by Microsoft Purview Information Protection, migration requires additional planning.

Key considerations:

AreaConsideration
Sensitivity LabelsSource tenant labels may not directly map to target tenant labels
EncryptionEncrypted files may require decryption or relabeling
DLPTarget tenant DLP policies must be reviewed
RetentionRetention policies may need redesign
Access ValidationSample protected documents must be tested after migration

Recommended Approach​

  1. Inventory sensitivity labels and protected files.
  2. Identify encrypted or restricted documents.
  3. Define source-to-target label mapping.
  4. Validate sample migration.
  5. Reapply target tenant labels where required.
  6. Confirm user access after migration.

Regional Policy Separation in a Single Tenant​

A single Microsoft 365 tenant can still support different policies by region or business unit.

The recommended design is group-based policy assignment, not domain-based policy assignment.

Policy AreaRecommended Scope
Conditional AccessUser or security group
IntuneUser group or device group
DefenderUser, device or policy group
DLPUser, group or workload scope
Sensitivity LabelsLabel policy assignment
SharePoint Download RestrictionApplicable site controls and Conditional Access scope; test exceptions against both

Administrative Units for Regional Delegation​

Microsoft Entra Administrative Units can provide limited regional administration.

Use cases:

  • Regional password reset
  • Regional user management
  • Help desk delegation
  • Limited device administration

Important limitation:

Administrative Units scope supported Entra directory roles to users, groups and devices. They do not scope Intune device-management permissions or hide all directory objects. Use Intune RBAC and scope tags for Intune administration, and retain separate tenant-isolation decisions. See Administrative Units.

Download Restriction and SharePoint Limited Access​

For SharePoint and OneDrive content, Conditional Access and configured SharePoint unmanaged-device controls can provide limited web access. The result depends on policy scope, device state and supported clients; being a guest or an employee does not set it automatically. Other workloads require their own access design. See unmanaged-device access controls.

Example model:

ScenarioAccess design to configure and test
Guest or internal user on an unmanaged deviceLimited browser access without file download, print or sync when the applicable policy requires it
User on a managed deviceAccess follows permissions and other policies; verify the supported browser and operating system
Regional exceptionDefine and approve policy scope explicitly; regional membership alone grants no exception
Privileged userAdministrative privilege alone is not a download exception

Global Tenant Consolidation Considerations

Mail Coexistence Strategy​

테넌트 통합을 시작하기 전에 이전 기간의 메일 송수신 경로를 정합니다.

다음처럼 두 환경을 함께 사용하는 동안에는 사용자별 메일 전달 경로를 시험하세요.

  • Notes + Exchange Online
  • Google Workspace + Exchange Online
  • Multiple Exchange Online Tenants
  • Shared SMTP Domain Environment

Key Design Principles​

  • Primary SMTP 유지
  • Alternate SMTP 설계
  • Mail Forwarding 구성
  • Mail Contact 활용
  • Mail Routing 검증

Shared Domain Migration​

같은 SMTP 도메인을 대상 테넌트로 옮길 때는 계정·그룹·별칭의 도메인 사용 현황과 제거 조건을 먼저 확인합니다. 다음은 작업 순서를 요약한 것으로, 실제 전환 전에는 복구 조건과 사용자 영향을 별도로 검토하세요.

Current State​

Tenant A

user@company.com

Target State​

Tenant B

user@company.com

Migration Procedure​

  1. Source Tenant Domain 제거
  2. Target Tenant Domain 추가
  3. User SMTP Reassignment
  4. Mail Flow Validation
  5. Teams Federation Validation

Risks​

  • Mail Delivery Failure
  • Teams Chat Failure
  • Guest Access Loss
  • Login UPN Change

Teams Identity Impact​

테넌트를 옮길 때 다음 정보가 그대로 유지된다고 가정하지 마세요. 선택한 이전 도구의 지원 범위와 대상 계정으로 접속한 결과를 확인합니다.

User Impact​

  • Teams Chat History
  • Teams Membership
  • Private Channel Membership
  • Shared Channel Membership
  • Guest Invitations

Recommendation​

기존 테넌트를 유지하면서 협업만 연결할지, 사용자 자료를 실제로 옮길지 먼저 결정하세요. 동기화는 자료 이전을 대신하지 않습니다.

Sensitivity Label Migration​

Microsoft Migration Orchestrator는 메일, OneDrive, Teams 채팅·모임을 함께 옮길 수 있습니다. 계정 자체와 SharePoint 사이트·Teams 채널은 별도로 준비해야 합니다. 지원 범위와 선행 조건을 확인하세요.

Purview Information Protection으로 보호된 자료는 이전 전에 레이블과 암호화 정책을 검토합니다.

Considerations​

  • Label Mapping
  • Encryption Removal
  • Rights Migration
  • Label Reassignment

Risk​

암호화된 문서의 이전 가능 여부는 도구와 암호화 방식에 따라 다릅니다. 파일을 옮긴 뒤에도 대상 계정이 열 수 있는지, 원본 테넌트의 키와 권한에 계속 의존하는지 시험하세요. 암호화 해제나 레이블 변경이 필요하다면 자료 소유자와 보안 담당자의 승인을 먼저 받습니다.

Regional Security Policy​

하나의 테넌트에서도 사용자·기기 그룹에 따라 지역별 정책을 다르게 적용할 수 있습니다. 제품별 할당 범위와 예외 처리 방식을 확인하세요.

Supported Controls​

  • Conditional Access
  • Intune Policy
  • DLP
  • Sensitivity Labels
  • Defender Policies
  • SharePoint Access Control

Design Principle​

정책을 사용자·기기 그룹에 할당하고 담당자가 그룹 구성원과 예외를 관리합니다. 도메인 이름만으로 조직의 정책 경계가 만들어지지는 않습니다.

Administrative Units​

Administrative Units로 일부 사용자·그룹·기기의 관리 권한을 지역별로 위임할 수 있습니다. 테넌트 전체를 격리하는 기능은 아니므로 지원되는 역할과 작업 범위를 확인하세요.

Example​

Korea Admin

  • Password Reset
  • User Management

Myanmar Admin

  • Password Reset
  • Device Management

HQ Admin

  • Global Administrator

Download Restriction Model​

Conditional Access와 SharePoint의 제한된 웹 접근 설정으로 비관리 기기의 다운로드를 제한할 수 있습니다. 게스트나 관리자라는 이유만으로 허용·차단이 결정되는 것은 아닙니다.

Typical Scenario​

대상확인할 접근 조건
게스트대상 사이트 권한, 기기 상태와 제한된 웹 접근 적용 여부
직원기기 준수 상태, 자료 보호 정책과 다운로드 허용 조건
관리자관리자 권한과 자료 접근 권한을 구분하고 예외 필요성 검토
지역별 사용자승인된 그룹별 예외와 만료일
